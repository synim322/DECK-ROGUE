# 00. Vision и продуктовые принципы

> **Канон видения:** отдельный файл [`Doc/00_VISION.md`](00_VISION.md) (фиксация 2026-11-23). Ниже — сжатая копия столпов; при конфликте побеждает `00_VISION.md`.

## High concept

**DECK//ROGUE** (рабочее название) — симулятор диджея в pixel-art roguelite-оболочке: почти полноценный пульт (с упущениями сложного), живой клуб, рандомная цепочка площадок с разным techno-саундом, проход дальше только по реакции зала, босс-клубы как сюжетные якоря.

**One-liner:** «Сводишь сет — зал решает, пустят ли тебя в следующий клуб».

**Fantasy:** ночь в духе живого techno-клуба (референс атмосферы — Mutabor): разные площадки, смена пластинок, динамика пульта, реакция танцпола. Прогрессия внутри сета и общая (забег/мета) ощущаются **по-разному**.

## Целевая аудитория — гипотезы

1. Любители музыкальных и ритм-игр (интерес к звуку и выразительным действиям).
2. Любители системных roguelite, коллекционирования и построения синергий.
3. Слушатели электронной музыки и начинающие диджеи; игра НЕ требует профессиональных навыков.

**Не ориентируемся на:** полнофункциональную замену Rekordbox/Serato, музыкальную DAW, симулятор клуба с реалистичной экономикой, хардкорный rhythm-action на рефлексах, босса как мини-игру вне диджеинга.

## Столпы дизайна

1. **Sound-first:** действие реально меняет услышанную музыку. Нельзя повышать счёт за звуковой хаос.
2. **Living club:** зал реагирует на выступление; проход в следующий клуб зависит от этой реакции.
3. **Dual progression:** внутри сета ≠ забег/билд ≠ мета-unlocks; нельзя свести всё к одной шкале «набери больше X».
4. **Club variety + random route:** у клубов разная музыка/вкус; обычные клубы в забеге в случайном порядке; боссы — сюжетные клубы.
5. **Almost-full deck, smart cuts:** пульт близок к диджейскому, сложное (ручной битмэтчинг, DAW, user tracks) сознательно упрощено/вынесено.
6. **Player agency:** нет единственной «правильной ноты»; плавное сведение, cut, дроп — валидные пути.
7. **Roguelite synergy:** улучшение меняет тактику и по возможности звук/управление.
8. **Cross-platform by construction:** одни правила на Windows, Web и Android.
9. **Readable pixel art + short sessions:** контролы важнее декора; MVP 5–7 мин, полный забег 15–25 мин.

## Уникальная особенность

Не «нажимать под готовый трек», а **вести ночь**: менять пластинки, сводить, читать зал. Рандом влияет на маршрут клубов и средства, но музыкальная согласованность внутри площадки гарантируется контентом.

## Важные ограничения

- Каждый музыкальный stem должен быть юридически доступен для интерактивного использования.
- В Web нельзя предполагать полноценный Unity AudioMixer с эффектами: см. [06](#section-07), [08](#section-09).
- Внешние песни пользователя, свободное смешивание BPM и time-stretching **не входят в MVP**.
- Эффекты не должны вызывать неприятные пиковые громкости; нужен лимитер/контроль мастера там, где он доступен.

## Цель прототипа

Проверить: «Хочется ли 5 минут подряд сводить подготовленные лупы и повторить забег ради нового музыкального билда?» Если нет, добавление лора, красивых клубов и метапрогрессии не спасёт core loop.

## Гипотезы и критерии (первый тест с 8–12 участниками)

- ≥70% понимают базовый переход после обучения без объяснений разработчика.
- ≥60% добровольно запускают ещё один забег.
- ≥70% называют хотя бы одно действие, которое улучшило звучание.
- Не более 1 критической аудиоошибки на ~30 минут теста в каждом обязательном браузере.

Это **ориентиры для команды**, а не известные рыночные нормативы.

# 01. Game Design Document (GDD)

**Версия:** 0.1 · **Дата:** 2026-11-11 · **Владелец:** Game Design  
**Связанные документы:** [Vision](#section-01), [DJ](#section-03), [Счёт](#section-04), [Прогрессия](#section-05), [MVP](#section-15).

## 1. Pitch

Симулятор диджея в pixel-art roguelite-оболочке: почти полноценный пульт, живой клуб, techno-разнообразие (референс Mutabor), рандомный порядок обычных клубов, босс-клубы как сюжет. Проход дальше — по реакции зала. Две разные прогрессии: внутри сета и общая (забег/мета). Канон: [`00_VISION.md`](00_VISION.md).

## 2. Core loop

`Случайный клуб → Briefing → Свести / сменить треки → Реакция зала → Проход? → Награда → … → Boss-клуб → Финал или поражение`.

Краткий цикл внутри одного выступления: `заметить потребность зала → выбрать следующий трек → подготовить деку → свести и изменить динамику → получить слышимую и визуальную реакцию → адаптироваться`.

## 3. Session structure

### MVP (P0)

- 1 тестовая локация, 2 выступления подряд по 100–140 секунд (весь забег с выбором награды ~5–7 минут).
- 4 пластинки × 3 stems (LOW, PERC, MUSIC); каждая 8 тактов/16 секунд при 120 BPM, с гарантированно совместимыми тональностями.
- Особое правило только у второго сета: seed выбирает одно из `maintain_energy` и `perform_one_clean_drop`. Первый сет — обучение, без особого правила. Контракт DJ-013 записан в ClubDefinition.
- 2 из 3 улучшений между выступлениями — срез DJ-014. В DJ-013 карточек нет: победа первого сета ведёт во второй.
- Первое выступление: закончить с `Hype ≥ 60`; второе: `Hype ≥ 65` и выполнить особое условие.
- Поражение сразу, reason `hype_floor`: `Hype = 0` дольше одной фразы (16 с). Конец таймера без цели — `timeout`. Победа первого сета продолжает забег; победа второго или любое поражение заканчивает его и делает Reset.
- Стартовый Hype каждого сета = 35 и не переносится. Reputation копится, Combo сбрасывается в ×1. Числа — гипотеза плейтеста.

### Полная версия (P1/P2) — по Vision

- Пул обычных клубов с разной музыкой; порядок **рандомный** (seed).
- 3–4 акта: случайные клубы → **boss-клуб** (сюжетная площадка) → дальше / финал.
- Средний забег 15–25 минут; редкие пластинки, разные стратегии.
- **Dual progression:** внутрисетовые фазы/запросы/Combo ≠ билд забега ≠ мета-unlocks выбора (не линейный +% Hype).

## 4. Выступление

### Фазы

1. **Briefing (до запуска):** имя клуба, жанровый вкус, цель, лимит времени, стартовые пластинки. Игрок может прослушать каждый трек в режиме cue (в MVP — превью через UI до старта, при необходимости без одновременного live-monitor).
2. **Performance:** таймер, Hype, Combo, Reputation, деки и световой feedback.
3. **Result:** победа/поражение, очки и объяснимые причины; в победе — выбор награды, кроме финального выступления.

### Неочевидная важная вещь

Нельзя принуждать игрока к единственной заранее прописанной кнопочной последовательности. Успех начисляется за свойства музыкального результата (соблюдение фразы, чистота баса, разнообразие, попадание в вкус клуба), а не за точную комбинацию команд.

## 5. Механические ресурсы

- **Hype:** от 0 до 100, ресурс выживания и цель испытания.
- **Combo:** множитель за качественные и разные действия; ошибка может сбросить его.
- **Reputation:** очки выступления / статистика забега.
- **Pulses of Tension (внутренний параметр):** краткосрочное напряжение для дропа; в MVP может отображаться простым индикатором «BUILD» без числовой шкалы.
- **Deck Loadout:** две активные пластинки, доступная библиотека из четырёх.

## 6. Что считается навыком

- Хорошее время запуска и перехода (фразировка), а не миллисекундный twitch-game.
- Работа с контрастом энергии и грамотное развитие сета.
- Чистое сочетание басов и музыкальных слоёв.
- Умение адаптировать переходы под текущую задачу.
- Применение билда; понимание его слабостей.

## 7. Управление и поддерживаемые форматы

- Windows: мышь/клавиатура, 16:9 с адаптацией.
- Web: desktop Chrome, Firefox, Edge; Safari — тестируется до обязательного включения. Аудиозапуск только после жеста пользователя.
- Android: **landscape, native build**, два больших контроллера/панели и одновременный multitouch; без требования физической клавиатуры.
- Browser on Android: **не обещаем паритет в MVP**, даже если версия Web способна запускаться.

Подробности см. [UI](#section-12) и платформенные документы.

## 8. Состояния игры

`Boot → AudioUnlock → MainMenu → PreClub → Performing → Result → Reward → PreClub → FinalResult`.

Срез DJ-013 экран Reward пропускает: победа сета 1 идёт с Result во второй сет. Награду между сетами ставит DJ-014.

Пауза во время аудио: паузируется одновременно игровая шкала и все деки. При возвращении из background не «догонять» время и не штрафовать игрока; переинициализировать расписание при необходимости (особенно Web).

## 9. Failure and fairness

- Ошибки объяснимы («басовый конфликт», «переход мимо фразы», «слишком долго один и тот же грув»).
- Рандом выбирает только из музыкально совместимого контента.
- Предупреждение до критического снижения Hype (например, при Hype < 20).
- Нельзя потерять из-за пропуска browser resume, нулевой громкости системного микшера, лагов при загрузке/в свёрнутой вкладке — такой сценарий ставит игру на паузу или предлагает рестарт выступления.

## 10. Контент и атмосфера

Ночной подпольный город в языке **JRPG-inspired premium pixel** (референс духа: Octopath / Sea of Stars storytelling-кадр): живой зал сверху, читаемый DJ-пульт снизу. У каждого клуба — своя палитра, архитектура света, поведение толпы и запросы к сету. Лор — короткие реплики промоутера и плакаты, не перекрывает пульт. Канон направления: [`19_ART_DIRECTION_JRPG.md`](19_ART_DIRECTION_JRPG.md); контент клубов: [05_CONTENT_BIBLE](#section-06).

## 11. Definition of fun

Если убрать весь арт и выдачу наград, у игрока остаётся музыкальный микшер, позволяющий **осмысленно создать красивый переход**. Если это не работает — GDD нужно пересмотреть, а не расширять.

## 12. Вне области MVP

Многопользовательский режим, собственная загрузка музыки, ручной битмэтчинг, сложная тональная совместимость, собственная DAW, генерация музыки нейросетью, VR, полноэкранные видеоклипы, онлайн-лидерборды, сложная экономика/микротранзакции, iOS.

# 02. DJ-механики и управление звуком

## 1. Музыкальная единица

**Пластинка** = синхронизированный 8-тактовый луп, состоящий из трёх аудиослоёв:

- `LOW`: kick + bass.
- `PERC`: hats, percussion, дополнительные ударные.
- `MUSIC`: synth, chord, melody, atmosphere.

`BPM=120`, `meter=4/4`, `barsPerLoop=8`, `secondsPerBeat=0.5`, `secondsPerBar=2`, `secondsPerLoop=16`. Все слои одного трека начинаются в одной точке и имеют одинаковую длину. Рекомендуется одна тональная группа для MVP.

## 2. Две деки

Каждая дека имеет `Empty / Loaded / Queued / Playing / Paused`, назначенную пластинку, уровень громкости, bass kill, положение фильтра и фазу трека. Нельзя загрузить новую пластинку поверх звучащей деки без управляемого `stop/load/start` (без внезапного обрыва). На старте A играет, B готова к cue.

### Основные команды

| Command | Правило | MVP |
|---|---|---|
| LoadTrack(deck, id) | Разрешена если дека не играет либо через отложенную смену | P0 |
| QueueStart(deck, boundary) | Квантизация к ближайшей будущей доле/такту/фразе | P0 |
| Stop(deck) | Короткая fade-out защита от щелчков | P0 |
| SetCrossfader(0..1) | Управляет слышимостью A/B | P0 |
| SetBassKill(deck, bool) | Глушит stem `LOW`, с плавным гейном | P0 |
| SetFilter(deck, 0..1) | Low-pass amount (0 open → 1 closed); сглаживание; **слышен** | P0 после Web Audio Gate / ADR; Act1 Mixer depth обязателен |
| SetPercTrim(deck, 0..1) | Gain стема PERC на деке | P1 Act1 Mixer depth |
| SetMusicTrim(deck, 0..1) | Gain стема MUSIC на деке | P1 Act1 Mixer depth |
| SetLoopLength(deck, 1\|2\|4\|8) | Длина лупа; apply quantize start (1–2→bar, 4→half-phrase, 8→phrase) | P1 Act1 Mixer depth |
| CueReady (state) | Loaded+Queued ≥1 бар на неиграющей деке | P1 Act1 |
| Hot Cue / EQ3 / send FX | Развитый DJ-контроль | P2 / вне Act1 must-ship |
| LoadFromCrate(deck, trackId) | Mid-set load из run-crate; на Playing — запрещён (нужен Stop) | P1 Act1 |
| QueueLoadPhrase(deck, trackId) | Load применяется на границе **фразы** (8 bars), mid-phrase → `QueuedLoad` | P1 Act1 |

### Deck management depth (P1 Act 1) — поверх P0, не ломая FIRST GIG

P0: две деки, load/queue на такт, библиотека 4, без crate mid-set. P1 Act1 добавляет давление на *управление деками*; зал реагирует на готовность и чистоту смены пластинок, не только на итоговый Hype.

1. **Phrase-locked load:** `LoadTrack` / `LoadFromCrate` на неиграющую деку встаёт в `QueuedLoad` до границы фразы.
2. **Mid-set crate:** run-crate стартует с 4 MVP-треков, cap Act1 = 8; mid-set можно грузить только на Empty/Stopped/Paused.
3. **Library pressure:** нужный energy-класс часто в crate — навык «что держать на B».
4. **CueReady:** неиграющая дека Loaded+Queued ≥1 бар → флаг для запросов клуба и `CleanPrepTransition`.
5. **Dual-deck constraints:** `DeadAir` (обе деки неслышимы >2 доли); `HotSwapFumble` (Stop доминирующей mid-phrase без handoff).

Клубные запросы (внутри сета, seed, ≤1 активное окно): `request_prep_b`, `request_energy_shift`, `request_swap_before_phrase`. События скоринга — §03.

### Mixer depth (P1 Act 1) — не ломает FIRST GIG

Канон GDD: [`01_GDD.md`](01_GDD.md) §3.4. **P0 FIRST GIG** — базовые контролы (Play/Stop/Crossfader/Bass Kill + filter по ADR). Mixer depth = Act1 слой: Filter `0..1` per deck, MUSIC/PERC gain `0..1`, Loop Length **`1|2|4|8`** (quantize start). AudioSpike / filter backend — Act1 gate для *слышимых* knobs, не блок MVP.

Удачные жесты → **CrowdMotion** tier bump (0..3, runtime `cheerIntensity`) + Hype: `CleanTransition`, `Drop`, `CueReadyHonor`, `CleanPrepTransition`, **`FilterPhrase`**, **`StemPunch`**, **`LoopSnap`**. Антифарм: крутилка без слышимого Δmix **≥1 bar** / без boundary не кормит; один `eventId` — одна награда. Числа — гипотезы (§03).

### Кроссфейдер

`x∈[0,1]`; для плавного уровня предпочтителен equal-power:

- `gainA = cos(π · x / 2)`
- `gainB = sin(π · x / 2)`

Добавить сглаживание гейна (например, 10–30 мс как стартовая гипотеза), чтобы быстрый жест не давал щелчков. Экстремумы `x=0`/`1` должны точно отключать противоположную деку. Учитывать клиппинг суммарного микса, держать headroom на master.

### Bass Kill

Для MVP **не нужен сложный EQ**: тумблер `LOW` stem с автоматическим коротким fade-in/fade-out. Это реально меняет звук и одинаково реализуемо на всех платформах посредством громкости отдельного stem. Позже — 3-полосный EQ.

### Фильтр

Нативный AudioLowPass/AudioMixerFilter нельзя считать кроссплатформенной готовой функцией: в Unity Web поддержка AudioMixer ограничена громкостью. Правильное решение — `IAudioBackend` + тестовый Web Audio `BiquadFilterNode`; fallback — заранее экспортированные фильтрованные версии stems, если выдержаны память и качество. **Не выкатывать на Web неработающий регулятор.** Act1 Mixer depth требует *слышимый* low-pass `0..1` per deck на всех Act1-targets.

### Stem gains (Act1 Mixer depth)

`SetPercTrim` / `SetMusicTrim` — независимые gains `0..1` на стемах PERC и MUSIC; LOW остаётся у Bass Kill + deck/crossfader gains. Сглаживание как у bass kill (10–30 мс). `MixSnapshot` несёт фактические stem gains для `StemPunch`.

### Loop Length (Act1 Mixer depth)

`SetLoopLength(deck, 1|2|4|8)`; apply только на квантованной границе (1–2→bar, 4→half-phrase, 8→phrase) — без mid-bar cut. Успешная смена длины на слышимой деке → `LoopSnap`. Спам в одной фразе = один apply + overwrite queue; без повторного score. Ship-subset `4|8` допустим до полного audio, канон — `1|2|4|8`.

## 3. Квантизация

- Слышимо немедленно: движение кроссфейдера, Bass Kill, фильтр и stem trims (со сглаживанием).
- Квантизировать: запуск деки, смену музыкального лупа и **Loop Length** на ближайшую будущую допустимую границу; по умолчанию **следующий такт**, опционально «следующая фраза».
- Пользователь видит момент применения через анимированную сетку/индикатор `QUEUED → PLAYING` / `LOOP 1|2|4|8`.
- Если команда пришла слишком близко к boundary, backend выбирает **следующую** границу (без попытки запускать в прошлом).

## 4. Переходы

### Smooth transition

A звучит ≥1 такт; B запущена синхронно; кроссфейдер плавно проходит от A к B за ≥1 такт. Чистый бас и согласованная фраза дают высокий балл.

### Hard cut

A доминирует, B готова, смена основного звучания за ≤1 такта **на сильной доле границы фразы**. Может быть равноценна smooth-стратегии, но не при простом хаотическом переключении туда-обратно.

### Transition evaluator

Фиксирует **смену доминирующей деки**, а не каждое движение ползунка. Начало: A≥0.65 по слышимости и B≤0.35. Конец: B≥0.65 и A≤0.35. Дека должна действительно воспроизводить назначенный track. Минимальное время/звучание до и после предотвращают фарм. Окно оценки — от момента начала до завершения перехода; результат публикуется один раз.

## 5. Drop без кнопки «Drop»

Детектор работает на событиях игры, а не на аудиораспознавании PCM:

1. Есть устойчивый слышимый музыкальный микс.
2. На минимум один такт глобальная энергия LOW (с учётом gains и bass kill) опущена ниже порога, например `0.20`.
3. Игрок восстанавливает LOW выше `0.75` на музыкально значимой границе.
4. Возврат сопровождается реальной атакой музыкального stem; «минимум → максимум» в один кадр без подготовки не считается.
5. После успешного дропа кулдаун минимум 4 такта; повтор не должен фармить бесконечные очки.

Для альфа-версии упрощение допустимо: детектор по двум состояниям `LOW_CUT` → `LOW_RETURN`, зависящий от MusicClock. Визуальный feedback не должен опережать звук.

## 6. Антиэксплойты

- Повторный toggle без прослушивания — не награда.
- Бесконечные переключения A→B→A в одной фразе дают максимум одну оценку и штраф за суету.
- Не начислять бонус за нулевую/неслышимую деку.
- Пластинка должна быть активна достаточное время, например ≥1 такт.
- Награды за переход/дроп начисляются **однократно на событие с ID**.
- Результат зависит от реальной музыки, а не от состояния одной кнопки.

## 7. Feedback

- Колесо/волна деки двигается в музыкальном времени.
- Тиковая линия 4/4, подсветка первого бита и конца 8-тактовой фразы.
- Маркеры «чистый бас», «переход в фразу», «дроп», «ошибка» с коротким текстом.
- Толпа и свет реагируют на Hype и успешные музыкальные события (`cheerIntensity`), а не на каждую кнопку/крутилку.

## 8. PC и touch parity

Семантика действий идентична. На Android Bass Kill и Play должны быть крупными кнопками, кроссфейдер — большим горизонтальным контролом; сложные knob gesture не являются единственным способом. Не требовать одновременной точной манипуляции тремя ручками.

# 03. Hype, Combo, Reputation и баланс

**Внимание:** все числа v0.1 — стартовые гипотезы для плейтеста.

## Определения

- `Hype`: целое/дробное число `[0,100]`; главный ресурс зала. Не «здоровье игрока», а вовлечённость публики.
- `Combo`: целочисленный множитель `×1..×3` для Reputation, повышается при разных качественных музыкальных событиях и сбрасывается после грубой ошибки.
- `Reputation`: неотрицательные очки качества сета (не валюта, не замена Hype).
- `Tension`: временное состояние build-up, оцениваемое DropDetector; не расходуемая валюта.

## Стартовые правила

| Событие | Hype | Reputation (до Combo) | Ограничение |
|---|---:|---:|---|
| Чистый переход | +8 | +100 | один на завершённую смену дек |
| Удачный дроп | +12 | +140 | cooldown 4 такта |
| Выполнен запрос клуба | +2 | +30 | максимум раз в 8-тактовую фразу |
| Пассивное снижение интереса | -2 | 0 | раз в 8-тактовую фразу |
| Басовый конфликт | -6 | 0 | не чаще 1 раза за фразу, если конфликт устойчив |
| Не меняется грув ≥4 фраз | -4 | 0 | раз за каждые последующие 2 фразы |
| Грубый срыв квантизации | -4 | 0 | если запуск вручную без Sync доступен в будущем |

*Баланс на уровне конечной фразы, а не FPS-цикла.* Промежуточные значения могут быть `float`, округлять только UI.

### Deck-management события (P1 Act 1) — гипотезы плейтеста

Не входят в P0 FIRST GIG. Живут только в Performing; один `eventId` — одна награда; пауза / audio focus не штрафуют.

| ScoreKind / kind | Hype | Reputation | Условие (по MixSnapshot + deck state) |
|---|---:|---:|---|
| `CueReadyHonor` | +3 | +40 | Активен `request_prep_b`; неиграющая дека `CueReady` до конца окна (1 фраза) |
| `LateLoad` | −3 | 0 | Load/QueuedLoad завершился после окна запроса |
| `DeadAir` | −5 | 0 | Обе деки ниже порога слышимости >2 доли |
| `HotSwapFumble` | −4 | 0 | Stop доминирующей mid-phrase без handoff на другую слышимую деку |
| `CleanPrepTransition` (`CleanPrep`) | +2 | +30 | Поверх clean transition: B была `CueReady` ≥1 бар до старта смены дек, transition score≥70 |
| `FilterPhrase` (`filter_phrase`) | +4 | +50 | Доминирующая слышимая дека: \|Δfilter\|≥0.35, слышимое изменение **≥1 bar**, пик/конец на phrase или bar boundary |
| `StemPunch` (`stem_punch`) | +3 | +40 | ≥1 bar stem contrast (PERC **или** MUSIC ≤0.25 при другом ≥0.55 + LOW path) → restore ≥0.70 на boundary **или** punch-up Δ≥0.25 в armed drop; без BassConflict |
| `LoopSnap` (`loop_snap`) | +2 | +25 | `SetLoopLength` 1\|2\|4\|8 применился на quantize boundary, дека слышима, длина сменилась |
| `PhraseStart` (`phrase_start`) | +2 | +25 | Quantized start слышимой деки (gain≥0.35) на границе фразы (bar-in-phrase 0, beat 0); другая дека тоже играет и слышна. Тихая дека и старт не на фразе — 0 |
| `BassHandoff` (`bass_handoff`) | +3 | +35 | Обе деки playing и gain≥0.35 целый бар (≥2 с); ровно один LOW≥0.45, другой LOW≤0.20; выплата на границе бара. Одна дека — не handoff. В том же Observe, где есть `Drop`, handoff не создаётся |
| `LineLift` (`line_lift`) | +3 | +40 | Канальный фейдер LINE 0..1 (`SetLineGain`, дефолт 1, не кроссфейдер): провод ≤0.25 → ≥0.75 за ≥1 бар, дека playing, итоговый gain≥0.35, конец на bar boundary. Кроссфейдер без движения LINE не платит. Без слышимого Δ — 0 |

**CrowdMotion (Act1):** quality-события выше (+ базовые `CleanTransition` / `Drop`) пишут tier 0…3 (`cheerIntensity`); визуал density/bob/arms на 1–2 бара; в одном баре — **max** tier. Ориентир: Honor/Prep/LoopSnap/PhraseStart/BassHandoff=1, CleanTransition/FilterPhrase/StemPunch/LineLift=2, Drop=3 (StemPunch+Drop в том же баре — cap 3).

Антифарм: `CueReadyHonor` ≤1× на окно; `DeadAir` ≤1× / phrase; `CleanPrepTransition` на том же transition `eventId`; knobs без слышимого Δmix **≥1 bar** не создают quality; `FilterPhrase` / `StemPunch` / `LoopSnap` — ≤1× на kind на phrase; `PhraseStart` ≤1× / phrase / deck; `BassHandoff` ≤1× / phrase; `LineLift` ≤1× / phrase / deck. В одном Observe `LineLift` деки съедает её `PhraseStart`.

## Качество перехода

Оценка 0–100 по четырём составляющим (пример):

- `Phrase timing` — 35%; движение или завершение перехода рядом с музыкальной границей.
- `Bass cleanliness` — 35%; нет устойчивого двойного low-end.
- `Continuity` — 20%; новый трек слышим и не пропадает по ошибке.
- `Club match` — 10%; энергия/жанр попадают в запрос клуба.

`score ≥70` → Clean Transition, `50..69` → Neutral, `<50` → слабый. **Разным стилям (smooth / hard cut) разрешены отдельные условия phrase timing**, чтобы one-size-fits-all оценка не делала один стиль бесполезным.

## Риск двойного баса

Если обе деки имеют активный stem LOW, их эффективные коэффициенты `gain_low_A`, `gain_low_B` одновременно >0.45 **не менее 2 долей**, создаётся `BassConflictStarted`. Штраф один раз на событие, повтор не чаще раза в 8 тактов. Для crossfade с Auto Bass Ducking это событие может отсутствовать.

## Разнообразие

Отслеживать последние 4 фразы и типы событий (`SmoothTransition`, `HardCut`, `Drop`, `GenreMatch`). Повторение **одного и того же трека и той же доминирующей деки** без изменений постепенно снижает Hype. Не наказывать «стабильный хороший грув» раньше 4 фраз; тайминги подбирать по плейтестам.

## Combo

Возможное правило: один успешный тип действия повышает внутренний streak; 2 разных качественных события подряд → ×2, 4 → ×3. Повтор одного типа не увеличивает streak бесконечно. Ошибка `BassConflict` сбрасывает ×1, но Hype не теряется мгновенно в большом объёме из-за нескольких технических триггеров.

## Проверка достижимости цели

Старт `35 Hype`; за ~7 фраз базовая потеря = 14. Три хороших перехода (+24), два дропа (+24), два совпадения (+4) → 73. Значит достижение порога 60–65 *возможно*. Это не означает, что игра уже сбалансирована. Цель успеха для новых игроков и опытных нужно определить плейтестами.

## Условия поражения

- `Hype = 0` дольше одной фразы (8 тактов, 16 с) → поражение сразу, reason `hype_floor`. Ноль на одном тике сет не обрывает.
- Конец таймера без цели сета → reason `timeout`. Сет 1: только `Hype ≥ 60`. Сет 2: `Hype ≥ 65` и одно правило DJ-013. Пороги те же.
- Пауза, свёрнутая вкладка, потеря audio focus и технический stall: таймер сета стоит, Hype не штрафуется.

## Инварианты

- Суммарный Hype всегда в `[0,100]`.
- `Reputation >=0`.
- Никакой scoring не зависит от FPS.
- Один событие `TransitionCompleted` или `DropCompleted` может изменить счёт **не более одного раза**.
- Видимое сообщение о награде связывается с конкретным изменением звука.
- Состояния треков/деки подтверждены аудиобэкендом либо имеют корректное scheduled состояние.

## Playtest-настройки (в debug menu)

`initialHype`, `targetHype`, `passiveDecay`, `bassConflictThreshold`, `transitionScoreThreshold`, `dropCooldownBars`, `clubPreferenceWeight`, `sessionLengthBars`. Сохранять конфиг вместе с телеметрией, иначе сравнивать забеги некорректно.

# 04. Roguelite-прогрессия и билды

> **Vision rule:** прогрессия *внутри сета* и *общая* (забег + мета) — разные системы. Нельзя описать обе одной формулой «набери больше X». См. [`00_VISION.md`](00_VISION.md).

## Два слоя (полная фантазия)

| Слой | Примеры | Обнуляется |
|---|---|---|
| **Внутри сета** | Hype/настроение зала, фазы build→drop, локальный запрос клуба (`request_prep_b`…), Combo, Tension, `CueReady` | Каждый новый клуб/сет |
| **Забег** | Upgrade gear, run-crate пластинок, маршрут Act1, Reputation забега | Конец забега |
| **Мета** | `UnlockedTrackIds` (напр. `track_signal_carrier` после босса), клубы/gear unlocks, best run | Не обнуляется; расширяет *выбор*, не обязательный power creep |

## Внутри забега (MVP-срез)

В начале игрок получает библиотеку из четырёх пластинок; две назначены на деки, остальные можно выбрать перед переходом/между выступлениями. Выступление открывает награду. **Для MVP** случайно показываем **2 из 3** улучшений; выбираем одно. Улучшение действует во втором выступлении и после проигрыша исчезает.

Пул MVP:

1. **Auto Bass Ducking** — при реальном двойном low-end автоматически снижает бас неосновной деки; устраняет часть риска и слышимо очищает микс.
2. **Riser Machine** — добавляет авторский riser при подготовке дропа, `+4 Hype` к первому успешному дропу каждой фразы (не складывается бесконечно).
3. **Hard Cut Specialist** — идеальный быстрый cut на границе фразы получает `+4 Hype` и бонус к Reputation; плавный переход бонуса не получает.

### Что делает хороший билд

- Допускает другой стиль игры (а не только больше очков).
- Имеет реальную звуковую/управленческую обратную связь.
- Не выключает необходимость сводить музыку.
- Влияет на решения при выборе новых пластинок/клубов.
- Имеет понятный UI-текст с условиями активации.

## Расширение после MVP (P1)

### Архетипы

- **Bass Master:** рискованные басовые переходы, компенсация конфликтов, тяжёлые клубы.
- **Drop Machine:** длинная подготовка и мощные дропы, риск утомления публики.
- **Smooth Operator:** гармоничные долгие переходы, постоянный Hype без взрывных пиков.
- **Genre Jumper:** смена жанров и неожиданные, но чистые сочетания.

## Метапрогрессия (shell / Act1)

- Платная/игровая валюта не нужна; если вводится — только внутриигровая.
- Прогресс разблокирует **опции**, не `+30% Hype`.
- Локальный `SaveGame` (schemaVersion=1): `UnlockedTrackIds`, `UnlockedGearIds`, `UnlockedClubIds`, `BestReputation`, `Settings` (внутри — `tutorialCompleted`). Контракт: [`Core/Save`](../DJ/Assets/_Game/Core/Save) + §20.6.
- **Flush:** смена Settings; новый meta unlock; конец забега (`FinalResult`), если Reputation > `BestReputation`. **Не** mid-run / pause / каждый тик.
- **Lose / Reset run:** сбрасываются run-crate и run-gear; **meta и Settings не откатываются**. Boot гидрирует `MetaUnlocks.Hydrate(UnlockedTrackIds)`.
- Act1: `UnlockedGearIds` / `UnlockedClubIds` **сознательно пустые** (зарезервированы); клубы Act1 идут из pool без meta-gate.
- Act1 boss clear → `track_signal_carrier` в `UnlockedTrackIds` (и в run-crate этой победы).
- Pause/resume уже в MVP; **mid-run / resume закрытого забега — не сейчас (P1.5+).**

## Рандом и честность

- Генератор RNG принимает seed; одинаковый seed при одинаковых решениях должен порождать одинаковые выборы содержимого, кроме аудиособытий реального времени.
- Рандом не выбирает несовместимые музыкальные лупы; MVP все пластинки совместимы.
- Независимая логика для reward roll, club rule и start track order.
- При случайной награде гарантировать минимум 1 применимый выбор.

## Почему это roguelite, а не просто DJ-симулятор

Забеги ограничены выступлениями, задачи меняются, ресурсы обнуляются, награды меняют тактику, а проигрыш заставляет начать новую цепочку. Само качество музыки остаётся центральной компетенцией, а не заменяется случайными бонусами.

# 06. Audio Tech Design: синхронизация, stems, WebAudio

> **Критический документ.** Прежде чем делать арт и большой контент, подтвердить звук во всех обязательных средах. Аудиосистема — основной инженерный риск проекта.

## 1. Аудиоцели

- Два музыкальных деки × по 3 синхронных stems (`LOW`, `PERC`, `MUSIC`).
- Общий музыкальный таймлайн (BPM 120, 4/4, 8 тактов), независимый от FPS.
- Без слышимых щелчков, пропусков такта и накопления рассинхронизации.
- Crossfader и bass kill реально управляют звуком; фильтр работает или явно исключён из тестовой сборки.
- Один и тот же gameplay code получает **подтверждённые семантические события** от platform audio backend.

## 2. Почему нужен интерфейс аудиобэкенда

Unity на PC/Android использует развитую аудиосистему. На Web Unity строит звук поверх браузерного Web Audio; многие DSP-эффекты Unity **не поддерживаются**. В официальном руководстве Unity 6.3 для Web доступен `AudioSource.PlayScheduled()`, но AudioMixer на Web позволяет менять **только громкость**, не обычные эффекты; есть ограничение `AudioClip.Create(stream=true)` и риск глитча на петле AAC. Поэтому нельзя просто нарисовать UI-фильтр и рассчитывать, что native AudioMixer «заработает сам» в браузере.

**Архитектурный контракт:**

- `IAudioBackend`: `InitializeAfterUserGesture`, `LoadStems`, `ScheduleStart`, `ScheduleStop`, `SetDeckGain`, `SetStemGain`, `SetLowPass`, `GetAudioClock`, `GetTransportState`, `Suspend`, `Resume`, `Dispose`.
- `IMusicClock`: `GetBar`, `GetBeat`, `GetNextBoundary`, `ToAudioTime`; владеет временной сеткой, без `Time.deltaTime` как основы ритма.
- `DeckController`: orchestration, но не знает `AudioSource`/`AudioContext`.
- `GameplayEventBus`: `DeckStarted`, `TransitionCompleted`, `DropCompleted`, `AudioInterrupted`; scoring на **семантических** событиях.

## 3. Бэкенд A — NativeUnityAudioBackend (Windows/Android)

- Предпочтительно `AudioSettings.dspTime` + `AudioSource.PlayScheduled(time)` с lead time на загрузку/декодирование.
- Отдельные `AudioSource` на stems; плавная регулировка гейна; защита от обрывов.
- `AudioMixer` для мастер-громкости и доступных native FX. **Не допускать двойной обработки эффектов** при добавлении Web-моста.
- Учитывать аудиопаузу при уходе Android в background, смене audio route и телефонном звонке.

## 4. Бэкенд B — Web

### Вариант B1: Unity Web AudioSource для MVP

В Unity 6.3 Web официально перечисляет `AudioSource.PlayScheduled`, `Play`, `Stop`, `volume` как поддерживаемые. Это позволяет **протестировать** 2 деки и stem mixing без отдельного JS-движка. Но нужны реальные проверки: фазовая точность, gapless loop, поведение после tab switch, `AudioSettings.dspTime`, одновременные источники и декодирование. Unity Web AudioMixer ограничен громкостью: native low-pass эффект НЕ гарантируется.

### Вариант B2: BrowserWebAudioBackend (рекомендуем, если нужен реальный фильтр в Web)

JS `.jslib` bridge вызывает Browser Web Audio API: `AudioContext` (источник времени), `AudioBufferSourceNode` (плейбек и расписание), `GainNode` (кроссфейдер и bass kill), `BiquadFilterNode` (low-pass), `AudioParam` automation (плавные изменения). Stems загружаются в WebAudio через `fetch`/`decodeAudioData`, **не играть одни и те же stems одновременно через Unity и браузер**. Мост передаёт планируемое время запуска и состояние Unity, backend управляет аудио; Unity визуализирует события. Сохранять audio scheduling в WebAudio time, а не пытаться гонять миллисекундные события из C# через `Update()`.

**Gate:** на раннем spike сравнить B1 и B2. Решение зафиксировать в [ADR](#section-20). Для паритета фильтра предпочтительнее B2, но это дополнительная разработка и отдельная загрузка/размещение аудио. Не объявлять готовым до теста.

## 5. Autoplay / user gesture

На Web звук не должен запускаться без пользовательского жеста. Первый экран: большая кнопка **«Включить звук и начать»**; по ней `AudioContext.resume()` (или эквивалент Unity-процедуры) выполняется внутри обработчика пользовательского действия. Если аудио заблокировано — показать инструкцию; не расходовать игровой таймер. После возврата в активную вкладку можно требовать повторного действия.

## 6. Audio clock и фразы

`beatDuration = 60 / BPM` (0.5 с), `barDuration = beatDuration*4` (2 с), `phraseDuration = barDuration*8` (16 с). События `Beat`, `Bar`, `Phrase` вычислять от **audio clock origin** и времени аудиосистемы. Пороговый ввод «следующий такт» назначает время не ранее `now + schedulingLeadTime`. Одна команда `ScheduleStart` имеет свой ID и scheduled timestamp. При пересоздании backend origin и очереди корректно обнуляются.

## 7. Audio graph (концептуально)

```text
Deck A: LOW/PERC/MUSIC → stem gains → Deck A gain → (filter) ┐
                                                         Master → Output
Deck B: LOW/PERC/MUSIC → stem gains → Deck B gain → (filter) ┘
```

- Crossfader: `gA=cos(pi*x/2)`, `gB=sin(pi*x/2)`.
- Bass Kill: target gain LOW = `0/1`, fade 10–30 мс (гипотеза).
- Filter: lowpass cutoff по экспоненциальной шкале частот, сглаживание параметров; без резких скачков gain.
- Master headroom: подготовленные stems с запасом; проверять пиковый уровень в реальном миксе.

## 8. Аудиоконтент и память

Четыре пластинки × три stems = 12 аудиофайлов. 16 с × 48 000 Hz × 2 каналов × 4 байта × 12 ≈ **73,7 MB** только PCM после декомпрессии, без движка и других ассетов. Это **оценка**, браузерный decode/resample и overhead могут изменить её. Не загружать бесконтрольно все будущие треки. Проверять размер RAM и decode time на реальных Android / desktop browsers. Для MVP можно сделать моно там, где не требуется стерео, но не жертвовать качеством из-за произвольной цифры.

## 9. Техническая приёмка — Audio Gate A0

1. После явного запуска звук идёт в Win build + Chrome + Firefox + Android native.
2. Слуховая проверка двух одновременных tracks и переключений `A↔B`, без щелчков.
3. 5 минут игры при искусственном снижении FPS: расхождение stems/битов **целевой ориентир ≤20 мс** (проверяется записью/анализом; точный порог уточнить).
4. 50 последовательных loop boundaries в Web без систематических gap/click; для Web Unity документирует потенциальную AAC-проблему.
5. 20 циклов `Pause / resume / background` без начисления score в тишине и без зависшего Play.
6. Android: входящий звонок/системное audio interruption, BT/проводные наушники — устойчивое восстановление.
7. Фильтр на каждой обязательной платформе реально меняет спектр либо по решению ADR имеет честную замещающую реализацию.

## 10. План борьбы с AAC loop glitches в Web

Unity 6.3 отдельно предупреждает о возможном искажении первых 1024 samples AAC; предлагает WAV source, предварительный silence/padding и корректный WAV `smpl` loop marker. Это **не универсальная гарантия**. Сначала тестировать реальные end-to-end зацикливания. Если проблема сохраняется, использовать запланированные соседние буферы/Web Audio own looping, экспортные корректировки и короткие fades на стыках; сохранить музыкальную фазу.

## 11. Запрещённые предположения

- «На Web работает весь AudioMixer, как на Windows» — **нет**.
- «`PlayScheduled` где-то упомянут, значит звук идеально синхронен» — **требует проверки**.
- «Можно запускать звук автоматически после загрузки страницы» — **нельзя считать допустимым**.
- «Можно использовать OnAudioFilterRead на Web» — **нет гарантированной scriptable DSP pipeline**.
- «Все Android телефоны имеют одинаковую задержку» — **нет**.

# 07. Unity-архитектура (C#, многоплатформенность)

## Принципы

1. **Game logic не знает платформы.** Scoring не имеет зависимостей от `AudioSource`, браузера, touch или размера экрана.
2. **Audio — абстракция с контрактом времени.** Native и Web могут иметь разный backend; на верхнем уровне они дают один набор событий.
3. **Data-driven**: пластинки, клубы, правила, эффекты и баланс — данные (`ScriptableObject`/JSON), без огромного `switch`.
4. **Тестопригодность**: MusicClock с подменяемым временем, чистые transition/drop evaluators и deterministic RNG.
5. **Vertical slice сначала.** Не внедрять DI-фреймворк, ECS, сервисный локатор и адресаблы до реальной необходимости.

## Слои

```text
Presentation (UI, PixelArt, InputAdapters)
            ↓ commands / readonly view-models
Application (RunController, DeckController, ClubDirector)
            ↓ domain services + ports
Domain (TransitionEvaluator, DropDetector, HypeSystem, RewardRoll)
            ↕ contracts
Infrastructure (UnityNativeAudio, BrowserWebAudio, DataStorage, Settings)
```

**Зависимости должны смотреть внутрь.** Domain не вызывает UnityEngine. Application может использовать адаптеры событий. Наблюдаемое состояние передавать через простые readonly snapshots/event notifications.

**Рекомендуемое решение по UI:** Unity uGUI как прагматичный вариант первой версии с Slider/Button/Canvas и отдельными prefab desktop/touch. UI Toolkit возможен, но для быстрых multi-touch slider interactions нужно проверить поведeние; не смешивать два стека ради моды.

## Сцены / состояния

- `Boot`: платформа, версии, разрешения, загрузка minimal assets.
- `MainMenu`: настройки, старт, unlock audio на Web.
- `Game`: brief + performance + overlay без лишних scene load.
- `Results`: итог/статистика/награда; для P0 можно как UI state внутри Game.

`RunState`: `Menu`, `PreClub`, `Performing`, `Paused`, `Result`, `Reward`, `Finished`, `Failed`, `AudioError`. State machine явно запрещает Score events вне `Performing`.

## Протокол команд

Все команды имеют `commandId`, `runId`, `deckId`, `requestedAtAudioTime` (или input monotonic timestamp), `type`, `payload`.

**Поток:** `Input → Command queue → Validate → Schedule at audio boundary → AudioBackend ack → Domain event → Hype/ReplayLog → UI`.

В MVP можно обойтись без сериализуемой очереди команд, но ID нужно хранить для защиты от двойных событий. На Web подтверждение backend особенно важно, чтобы UI не рисовал ложное `PLAYING` до реального аудиостарта.

## Хранение

- `ScriptableObject`: статичные авторские данные (`TrackDefinition`, `ClubDefinition`, `UpgradeDefinition`).
- `JSON` локальный **SaveGame** (shell / early Act1): один документ `schemaVersion` + `settings` + unlock arrays + `bestReputation`. Ключ/файл стабильный (`deck_rogue_save_v1`). Web: IndexedDB/PlayerPrefs с учётом ограничений браузера; без облачной гарантии. Поля и flush — §20.6.
- `RunState` в памяти; mid-run save / продолжение закрытого забега — **не сейчас**; после page refresh — новый забег, meta/settings поднимаются из SaveGame.

## Сборка и CI

`main` — стабильная ветка, `develop` — интеграция, `feature/DJ-xxx` — задачи. Каждая фича: требования, unit tests, контроль ссылок, PlayMode smoke. На каждый milestone генерировать **Windows + Web + Android** smoke builds, даже если feature написана на ПК. При наличии Unity license/CI agent можно использовать batchmode builds, но не блокировать MVP из-за CI инфраструктуры.

## Версионность и ADR

Версия Unity фиксируется в `ProjectSettings/ProjectVersion.txt`; этот документ рекомендует семейство 6000.3 LTS на дату написания. Фактический minor/package versions подтверждаются после создания проекта. Любое изменение backend записывается в [ADR](#section-20). Данные: [20](#section-21).

# 08. Web: браузерная версия Unity

**Цель P0:** playable HTML/WebAssembly build на desktop Chrome/Firefox/Edge с музыкальной функциональностью core loop. Safari (desktop) — target после проверки; мобильные браузеры — необязательны для MVP, Android получает native build.

## Ключевые платформенные факты

- Unity 6 Web поддерживает браузеры с WebGL 2, WebAssembly и HTML5. Современные версии Unity описывают поддержку отдельных мобильных браузеров, но это **не гарантия** достаточной памяти/звуковой задержки на любом телефоне.
- Browser audio ограничивает autoplay: звук часто требует click/tap.
- Unity Web AudioMixer допускает управление **громкостью**, но не стандартными DSP-эффектами Unity.
- `AudioSource.PlayScheduled` указан среди поддерживаемых методов в руководстве Unity 6.3 Web Audio, **но реальные gapless loop и phase alignment проверить отдельно**.
- Для AAC есть документированный риск паузы/артефакта в петле. Исходники WAV + loop markers и WebAudio fallback описаны в [06](#section-07).
- `OnAudioFilterRead` и потоковая scriptable DSP-пайплайн недоступны/ограничены: не проектировать Web на этой предпосылке.

Подтверждённые ссылки: [TECH_SOURCES](#section-24).

## Web UX flow

`Page loaded → Start/Enable Audio button → backend unlock → prewarm/decode audio → start session → pause on hidden/unfocused → resume interaction → re-sync if needed`.

Не списывать Hype, пока audio context suspended, если потерялся focus или данные ещё декодируются. Ошибка loading → информативный экран Retry без потери забега.

## Desktop browser support matrix

| Браузер | Статус MVP | Что тестировать |
|---|---|---|
| Chrome latest Windows | P0 | autostart block, scheduling, AAC, tab suspend |
| Firefox latest Windows | P0 | browser audio clock, gapless, gain ramps |
| Edge latest Windows | P0 | аналогично Chrome, встроенные настройки autoplay |
| Safari latest macOS | P1/при доступе к устройству | Web Audio behavior, memory, fullscreen |
| Chrome Android | P2/эксперимент | мобильная память, события touch, audio resume |
| Safari iOS | вне MVP | PWA/browser audio ограничения |

Указание «latest» относится к моменту QA и фиксируется конкретной версией в test report.

## Web audio backend decision (A0)

1. Создать minimal Web build с **двумя деками × 3 stems**.
2. Проверить `AudioSource.PlayScheduled`, volume/bass kill, loop boundaries, 5-min drift и 20 tab suspends.
3. Для low-pass сравнить native Unity effect (ожидаемо не работает на Web) с JS Web Audio `BiquadFilterNode`.
4. Выбрать: **B1** (Unity audio for volume/scheduling + честно упрощённый фильтр) или **B2** (JS audio engine for Web, полноценный filter), записать ADR и остановить расширение, пока не достигнуты quality gates.

**Опасность:** нельзя одновременно играть stems из Unity и Web Audio — будет эхо/двойной громкости. Понадобится один источник звука.

## Загрузка и память

- Первая итерация: встроенные 12 short stems, не streaming, и фиксированный starter library.
- Аудио сжатое для сети, но проверить decode/RAM usage: `CompressedInMemory` vs `DecompressOnLoad` тестировать на целевых браузерах.
- Не считать размер итогового файла размером занимаемой RAM; при decode может потребоваться значительно больше.
- Web build: release compression Brotli если сервер умеет правильно отдать MIME + Content-Encoding; кешировать ассеты на повторном входе.
- **Ориентир:** общая первоначальная загрузка до 50 MB сжатых данных, старт <15 секунд на стабильном соединении — **целевые оценки**, а не гарантии движка.
- Учитывать browser memory limits, вкладки в фоне, перезагрузки контекста, WebGL context loss.

## Деплой

- HTTPS (кроме localhost), корректные заголовки сервером (`Content-Encoding`, Content-Type для wasm/data/js).
- Не открывать `.html` через `file://` — тестировать с HTTP-сервера.
- GitHub Pages/itch.io/собственный CDN — возможны; выбор площадки после проверки её требований и политики по Web сборкам.
- Проверять mobile responsive только как bonus, не обещать пользователю browser Android паритет с native.

## Browser integrations

MVP — без JS внешних SDK, cookies analytics и внешней авторизации. `.jslib` только при необходимости для собственного Web Audio бэкенда. В будущем можно сделать platform SDK за интерфейсом `IPlatformServices`.

## QA checklist

- [ ] Доступен экран с кнопкой `Enable Audio`.
- [ ] Звук играет только после разрешённого взаимодействия.
- [ ] Audio не сбивается после 5 минут и 50 loop boundaries.
- [ ] При уходе вкладки нет штрафов за тишину.
- [ ] Каждая управляющая кнопка работает мышью и клавиатурой.
- [ ] Старт/загрузка/ресет корректно обрабатывают network timeout.
- [ ] Кешированная и чистая загрузка; выключенный кеш; browser storage full.
- [ ] Игра не ошибочно обещает функциональность, не реализованную в Web.
- [ ] В консоли нет критических ошибок после полного забега.

# 09. Android: нативное приложение и touch-first UX

## Цель

Android — **отдельная нативная сборка Unity**, а не WebGL внутри контейнера. Сохранить общий игровой дизайн и музыку, но сделать контролы под пальцы.

## Важные решения

- Ориентация **landscape** для MVP (проверить на 16:9, 19.5:9, 20:9 и планшете).
- Большие touch targets; целевой минимум ~48 dp для важных кнопок, не декоративные пиксели.
- Кроссфейдер на нижней панели; две панели дек с крупным цветом и названиями.
- Одновременный ввод: палец на crossfader + другой на Bass Kill или Deck Play; multi-touch не должен ломать drag.
- `Screen.safeArea` / display cutouts, системный жест навигации и смена orientation безопасно обрабатываются.
- Без hover, правой кнопки мыши и клавиатуры для основных действий.

## Touch layout (предложение)

```text
┌──────────────────────────────────────────────┐
│  Hype / Time / Crowd (кратко)                │
├─────────────────────┬────────────────────────┤
│ DECK A              │ DECK B                 │
│ track / phase       │ track / phase          │
│ [PLAY] [BASS KILL]  │ [PLAY] [BASS KILL]     │
│ FILTER  ○────       │ FILTER  ────○          │
├─────────────────────┴────────────────────────┤
│ A  ──────[ CROSSFADER ]──────  B             │
└──────────────────────────────────────────────┘
```

При узкой ширине скрывать вспомогательные waveform/лейблы за кнопкой `DETAILS`, а не ужимать кнопки до непопадаемого размера. Клубная сцена может стать узкой декоративной полосой, если музыка требует места.

## Audio interruptions

- Получен звонок/уведомление, приложение ушло в background → `Pause` gameplay, запрос backend.Suspend(), сохранить текущий музыки/состояния.
- Вернулись → предлагать `Продолжить`; обновить audio clock origin, привязать stems к фразе, не проигрывать накопившиеся игровые штрафы.
- Bluetooth-наушники дают задержку: scoring считать по музыкальному времени, а не по визуальному времени кадра; дать настройку калибровки AV sync после MVP.
- Тестировать смену аудиовыхода, уровень media volume и режим без звука; при выключенном звукe игра может выводить предупреждение «Для полноценного опыта нужен звук» (не блокировать жестко устройство).

## Производительность и размер

- Функциональный ориентир: 30 FPS на выбранном среднем Android-устройстве, целевой 60 FPS на современном устройстве; **аудиоплейбек не может зависеть от FPS**.
- Минимизировать draw calls/pixel overdraw/тяжёлые 2D light/particle.
- Не держать одновременно десятки загруженных музыкальных stem packs.
- Сжатие аудио и текстур под Android выбирать после профилирования. Универсальных гарантий по устройствам нет.
- Проверять терморегуляцию после 20 минут, battery drain и state resume.

## Android UI/UX QA

- [ ] Все P0-команды выполняются touch, без клавиатуры.
- [ ] Два одновременных пальца корректно меняют crossfader и Bass Kill.
- [ ] Никаких критических кнопок под вырезом экрана/навигационной полосой.
- [ ] Можно прочитать track ID и фразу на маленьком телефоне.
- [ ] Сворачивание, звонок, screen lock → audio pause без потери сета.
- [ ] Шкала Hype и визуальный beat indicator не рассинхронизированы со слышимым звуком.
- [ ] APK/AAB релизные требования магазина проверены по актуальному регламенту непосредственно перед публикацией.

## Решения P1

- Виброотклик для переключателя/первого бита (опционально, может мешать музыке).
- Калибровка audio/video latency.
- Нативные уведомления, облачное сохранение и реклама **не нужны** для MVP.

# 10. PC: Windows desktop

## Приоритет релиза

Windows build — основная платформа разработки и локального тестирования. Веб и Android **не откладывать до окончания ПК-версии**: platform smoke с первых инженерных этапов.

## Системные цели, не подтверждённые измерениями

- Основная ориентация landscape, рабочий desktop aspect 16:9; поддержка оконного/полноэкранного режима.
- Целевой FPS 60 на умеренном железе; при падении FPS audio clock не уплывает.
- UI масштабируется, разрешения 1280×720, 1920×1080, 2560×1440 тестируются.
- Sound output на системное устройство, корректно работает после device switch (если driver/OS поддерживает).

## Предложенная клавиатура MVP

| Действие | Keyboard | Mouse |
|---|---|---|
| Play/Queue A | Q | Button A |
| Play/Queue B | P | Button B |
| Bass Kill A | A | Toggle A |
| Bass Kill B | L | Toggle B |
| Crossfader | ← / → или A/D только после переназначения | Drag slider |
| Filter A/B | Wheel over control или отдельный shortcut | Drag filters |
| Pause | Escape | Pause button |
| Load track | 1–4 в panel selection | Click card |

**Конфликт:** `A` занят Bass Kill A, поэтому не использовать WASD для crossfader одновременно. Конкретный keymap после прототипа закрепить в Input Actions; все команды доступны мышью.

## UX

- Графическая сцена клуба сверху, крупный микшер внизу; hover tooltip объясняет FX, но не требуется для Android.
- Единая шкала 4/4, заметный индикатор upcoming phrase.
- Системные настройки: master music volume, SFX volume, resolution/fullscreen, UI scale, reduced flashing, captions, audio output note.

## Публикация

- Первая self-hosted/itch.io demo или playtest ZIP; Steam/другие магазины — отдельное решение о правах, регионах и магазинах.
- Сборки подписывать и проверять на чистом ПК. Автообновление и cloud saves не нужны MVP.
- Поддержка Linux/macOS возможна позднее, но **не обещается** в v0.1.

# 11. UI/UX, onboarding и доступность

## Главная задача UI

Игрок должен мгновенно понять:

1. **Что сейчас слышно?** Дека A/B, пластинка, LOW active, crossfade position.
2. **Когда следующий музыкальный момент?** Бит/такт/фраза, queued actions.
3. **Чего хочет зал?** Hype, цель, активное требование, оставшееся время.
4. **Что дала моя команда?** Реальное звучание, короткий текст события, реакция публики.

## Экраны

| Экран | Содержимое | Переход |
|---|---|---|
| Start/Audio unlock | Title + «Включить звук и начать» (Web) | → Menu |
| Main Menu | Start Run, Settings, How To Play | → Briefing |
| Briefing | Название клуба, цель, стартовые tracks | → Performance |
| Performance | 2 decks, crowd, mixer, goal, beat grid, feedback | → Result |
| Reward | Выбрать 1 из 2 предложенных upgrades | → Briefing 2 |
| Results | Victory/Failed, Hype trace summary, points, explanation | → Menu |
| Settings | Music/SFX, accessibility, input/scale | → previous |

## Компоновка desktop

```text
┌───────────────────────────────────────────────────────────────┐
│ CLUB / TIMER                       HYPE / COMBO / REPUTATION   │
│                       PIXEL CROWD / LIGHTS                    │
├───────────────────────────────────────────────────────────────┤
│ DECK A [WAVE / PHRASE]           DECK B [WAVE / PHRASE]        │
│ track info + PLAY + BASS         track info + PLAY + BASS      │
│ FILTER             CROSSFADER                  FILTER         │
│                     FEEDBACK                                  │
└───────────────────────────────────────────────────────────────┘
```

Desktop на 16:9 показывает больше сцены. Android перенастраивает приоритет в пользу пульта ([09](#section-10)), не просто уменьшает Canvas.

## Visual language

- Сцена = JRPG storytelling plate; пульт = инструмент (см. [`19_ART_DIRECTION_JRPG.md`](19_ART_DIRECTION_JRPG.md)).
- A — холодная палитра, B — тёплая, но всегда **подписаны A/B** и отличимы формой.
- Линия сетки 4/4; первый бит группы визуально сильнее.
- Queued vs Playing vs Paused имеют разное текстовое состояние/иконку.
- Успешное действие: короткая надпись `CLEAN MIX +8`, мягкий accent wash и реакция зала. Ошибка: `BASS CLASH -6`, а не только красная вспышка.
- Переполненный UI опаснее недостаточной декоративности. Реакции ≤2 секунды и не закрывают crossfader.

## Tutorial MVP (до 90 секунд, пропускаемый)

1. «Дека A уже играет — послушай» (8–12 сек).
2. «Загрузи другую пластинку на B» (показать карту пластинок).
3. «Нажми START B — она запустится на следующем такте» (объяснить queue).
4. «Включи Bass Kill у одной деки, чтобы не спорили два баса».
5. «Проведи crossfader вправо» — первый удачный переход.
6. «Убери бас на такт и верни на сильную долю» — первый дроп.
7. «Вот что такое Hype, теперь ты сам».

Не выполнять за игрока действия во время обучения, кроме предустановленной исходной композиции. Существует `Skip Tutorial` + tooltips для повторного чтения.

## Доступность

- Reduced flashing — полностью выключает стробы, резкие белые flashes; default может иметь мягкие эффекты.
- Консервативные уровни громкости при старте и независимые Music/SFX sliders.
- Не полагаться только на цвет; icons + labels.
- UI-scale, минимальный читаемый кегль на телефоне, настраиваемые крупные кнопки.
- Текст feedback (`CLEAN MIX`, `BASS CLASH`) и понятный журнал последних 3 событий.
- Игра музыкальная: без аудио опыт неполный, но визуальный beat assistant и captions помогают ориентации; не заявлять полную доступность без тестирования с соответствующей аудиторией.
- На Android клавиатура не требуется; на ПК кликабельны все основные элементы.

## Экранные состояния ошибок

- `Audio requires interaction` → кнопка Resume Audio.
- `Audio files failed to load` → Retry / Back to menu.
- `Browser tab suspended` → paused overlay; timer не идёт.
- `Device performance low` → optional low-effects mode (P1).

## Проверка UX

В 8–12 первичных плейтестах без разработчика игрок должен за 90 сек понять: какая дека играет, как запустить B, зачем нужен bass kill, как работает crossfader и что такое Hype. Замерять число пропущенных инструкций и время до первого успешного перехода.

# 12. Pixel Art Style Guide

> **Art Direction Shift (канон):** [`19_ART_DIRECTION_JRPG.md`](19_ART_DIRECTION_JRPG.md) — *JRPG-inspired premium pixel*. Этот раздел — рабочие правила производства; north star и hero composition Act1/boss — в канон-файле.

## Визуальная идентичность

**Жанр:** JRPG-inspired premium pixel nightclub — storytelling-кадр зала (дух Octopath / Sea of Stars) + читаемый DJ-инструмент снизу. **Не** 3D HD. **Цель:** красивый ночной кадр, живая музыка через толпу/свет, пульт сводится без легенды, клубы отличимы при минимальном бюджете ассетов.

**Сохраняем:** 2D/pixel, Point/Nearest, зал сверху / пульт снизу, 3 Hype-состояния, A/B dual-coding, reduced flashing, короткий лор.  
**Меняем:** плоский «просто неон» → живописная глубина и mood-light; пятна толпы → pose language; строб как стиль → опциональный эффект.

## Технические параметры v0.1

- Базовое **пространство клубной сцены**: `480×270` logical pixels (16:9), кратные 16/8; художественный reference canvas, НЕ фиксированное разрешение интерактивного UI.
- Сетка деталей 8×8 и 16×16; значки 16×16/24×24; DJ ~32×48.
- Sprite import: Point/Nearest, без неуместного размытия, без subpixel jitter; единый PPU в масштабе.
- Unity Pixel Perfect Camera **для сцены**; UI — native-res при сохранении JRPG-UI языка.
- Без произвольных scale/rotation «лесенок»; мягкое свечение — отдельный lighting layer, не замена спрайта.

## Композиция кадра (hero rules)

```text
Верх ~45%: status strip + club storytelling plate (архитектура / толпа / сцена)
Низ  ~55%: BoothHud (деки, бит/фраза, пластинка, crossfader, bass kill)
```

Приоритет взгляда: задача зала + Hype → активная дека → бит/фраза → пластинка → кроссфейдер / bass kill. Декор не конкурирует с контролами. PreClub/плакат несут лор; Performing не засыпается абзацами.

**The Signal (boss):** та же сетка; мотив сигнала (луч/антенна/пустой центр); фазы = силуэт зала + подпись фазы.

## Палитра — Global UI / Booth (стабильная)

# 13. Audio Content Pipeline: производство, экспорт, тесты

> Music pools / rewards / dialects: [`16_MUSIC_ACT1.md`](16_MUSIC_ACT1.md).  
> Stem tech / RAM / folders: [`17_AUDIO_CONTENT_ACT1.md`](17_AUDIO_CONTENT_ACT1.md).

## Требования к музыкальной библиотеке

Для MVP производятся **4 оригинальных музыкальных лупа**, каждый разделён на 3 stems по 16 секунд при 120 BPM, 4/4, 8 тактов. Все слои синхронны, совместимы друг с другом по общей тональной группе, имеют одинаковую файловую структуру.

**MVP deliverables (P0 FIRST GIG):** 4×3 = 12 audio files, плюс при необходимости 1–2 коротких UI-SFX, 1 riser для upgrade; исходные DAW project files хранятся отдельно от Unity Assets.

### P1 Act 1 music slice (до The Signal)

| Slice | Композиции | Stems | Права |
|---|---:|---:|---|
| P0 core | 4 | 12 | test / gate |
| P1 must-ship new | 10 | 30 | **planned** (`PLANNED-ACT1-*`) |
| Deferred Dream/Rave | +4 | +12 | planned Act2 |

Не расширять `TrackLibrary.CreateMvp()`. Ship order: Warehouse unique → Bass unique → reward pools → Signal → Dream/Rave. Content gate: после A0 на P0.

## Слои

- `LOW.wav`: kick, bass, субниз; желательно без чужих hi-hat/melodic bleed.
- `PERC.wav`: hi-hats, snare, claps, shakers, percussion, часть transitions.
- `MUSIC.wav`: chord, pad, lead, atmospheres; строить так, чтобы временный low-cut не делал трек бессмысленным.

## Стандарт экспорта

| Параметр | Норма v0.1 |
|---|---|
| Mastering source | WAV PCM 48 kHz, stereo, 24-bit или float рабочий формат |
| Loop | 8 тактов, ровно 16.000 s при BPM=120 (кроме согласованного padding для Web) |
| Start position | Сэмпл 0 совпадает во всех 3 stems |
| End | Без хвоста, создающего audible click; tail согласован композитором |
| Loudness | Сопоставима во всём наборе, без digital clipping; сделать тестовую калибровку по результирующему миксу |
| Harmony | Одна обоснованная тональная группа для MVP |
| ID | `track_id/stem_name/version` |

**Не просто обрезать sample в момент, где он не равен нулю:** подобрать zero-crossing/микрофейды/хвосты и проверить phase continuity. Для реального loop со звуковыми хвостами возможна overlap-схема; решение влияет на scheduler.

## Импорт в Unity

- Оригинальные WAV — reference/master, рабочие imports можно сжать под платформу.
- Web может перекодировать исходники в AAC и изменять начало/конец — см. официальные Unity Web audio notes. Не считать экспортный WAV гарантией gapless в браузере.
- В Web memory tradeoff: `DecompressOnLoad` vs `CompressedInMemory`; проверить сам факт чистого looping на каждой настройке.
- Все 3 stems одной пластинки должны иметь одинаковую выбранную компрессию и envelope.

## Таблица качества (для каждого трека)

| Проверка | Как проверить | Pass |
|---|---|---|
| Самостоятельно | Слушать сумму 3 stems | Полноценный грув |
| Bass cut | Убрать LOW на 1–2 такта | Не распадается полностью музыкальная форма |
| Перекрёстный mix | Смешать с каждым из 3 других | Нет очевидной гармонической грязи |
| Фразировка | Запустить на bar 1 и bar 5 | Дроп/переход осмысленен |
| Loop gap | 50 повторов в actual platform build | Нет постоянного gap/click |
| Levels | Максимальная сумма 2 tracks | Без слышимого клиппинга |
| Licensing | Хранить источник сэмплов/договор | Права позволяют игру на PC/Web/Android |

## Audio naming и metadata

```text
AudioSources/
  track_neon_pulse/
    session.als  (пример: DAW-specific project, не обязательное имя)
    exports/
      track_neon_pulse_LOW_v01.wav
      track_neon_pulse_PERC_v01.wav
      track_neon_pulse_MUSIC_v01.wav
```

Собрать CSV/JSON манифест track metadata: ID, BPM, key, genre, energy, file checksums, loop bars, licensing status, reviewer.

## Права и безопасность

- Не импортировать чужие популярные треки без права на распространение, интерактивную обработку и публикацию в веб/мобильных сторах.
- Samples/loops: собирать конкретную лицензию и доказательство покупки/разрешения, а не предполагать, что «royalty-free = любые права».
- При работе с композитором письменно определить передачу/лицензирование master, stems, derivative works, streaming/interactive use, территории и срок.
- Учесть, что музыка внутри приложения не означает право продавать отдельный soundtrack.

## Content gate

Не производить 30 треков до прохождения Audio Gate A0 на двух тестовых пластинках и первого fun-test. Лучше 4 отлично совместимых грува, чем 30 случайных несовместимых лупов. Act 1 P1 (14 planned) стартует **после** P0 gate; каждый клубной пул проходит свой cross-mix check внутри семьи до добавления в билд.

# 14. MVP Specification / Acceptance Criteria

## Определение MVP

**FIRST GIG v0.1** — небольшой, полностью проходимый пиксельный DJ roguelite с **двумя выступлениями**, в котором можно свести музыкальные деки, слышать результат, получать очки, выбрать случайный upgrade и использовать его во втором выступлении. Нужны playable Windows/Web/Android builds.

## Игровые ограничения

| Объект | MVP P0 |
|---|---|
| Контент | 1 клуб (Neon Basement), 2 последовательных выступления |
| Время | 100–140 секунд на выступление, ~5–7 минут на забег включая награду |
| Музыка | 4 пластинки × 3 stems, 120 BPM, 4/4, loop 8 bars |
| Пульт | 2 деки, Play/Queue, Crossfader, Bass Kill, Low-pass (зависит от прохождения Web Audio Gate) |
| Scoring | Hype, Reputation, Combo, transition/drop/match evaluators |
| Рандом | стартовый порядок доступных пластинок, один из 2 клубных запросов, 2 из 3 upgrade карточек |
| Прогрессия | выбор 1 награды между выступлениями, сброс после забега |
| UI | menu, audio unlock, briefing, performance, reward, result, settings, tutorial |
| Арт | 1 JRPG-premium club plate, 3 состояния толпы, 2 анимированных диска, mood-light (не строб) |
| Сборки | Windows, desktop Web, Android native landscape |

## Scope lock: P0, P1, P2

### P0 — без этого MVP не готов

- [ ] Audiogate A0: две деки, stems, чистый loop на 3 платформах.
- [ ] Один аудиоисточник авторитетен на каждой платформе; нет двойного Unity + Web Audio.
- [ ] Рабочие Play/Stop/Queue, crossfader, Bass Kill; фильтр P0 **только после подтверждённого решения** (см. ADR-003).
- [ ] 4 музыкальные пластинки с правами и качественной совместимостью.
- [ ] Состояния двух выступлений, цели, таймер, pause/resume.
- [ ] Hype / Combo / Reputation, прозрачные причины начислений.
- [ ] Detectors перехода / bass conflict / drop с анти-фармом.
- [ ] 3 валидных upgrades, 2 предлагаются случайным образом, один выбирается.
- [ ] Раздельный desktop/touch UI; Android landscape; Web audio unlock.
- [ ] Pixel club + crowd feedback с reduced flashing.
- [ ] UX tutorial и экран результата.
- [ ] Автотесты домена и smoke/e2e чеклист всех сборок.

### P1 — следующая играбельная версия

Map nodes, 3–5 клубов, новые треки и жанры, Loop Length, Echo/Reverb (после анализа Web), контрастные билды, persistent unlocks, save-resume, полные tooltips, desktop Safari.

### P2 — после проверки аудитории

Ручной BPM / time-stretching, harmonic mixing между тональностями, расширенная DJ-симуляция, пользовательский контент, cloud saves, mobile browser polish, новые платформы, online leaderboards.

## Точная приёмка по вертикальным срезам

### Audio / Input

- PC: A и B всегда запускаются по музыкальной сетке и не расходятся за 5 минут; проверить метрономной/тестовой записью, ориентир ≤20 мс.
- Web: явное user gesture открывает AudioContext; 50 loops без систематического gap/click, 20 tab hide/resume без потерянной фазы; Chrome, Firefox, Edge.
- Android: все P0-действия доступны пальцами, multi-touch работает, audio focus interruption не даёт поражение.
- При движении crossfader звук реально меняется; при Bass Kill исчезает LOW, а остальные слои остаются.
- Filter (если оставлен в scope): audible low-pass на всех P0-targets. Не подменять UI-заявление тишиной.

### Gameplay

- Игрок может сделать **минимум 2 разных типа перехода** (smooth и hard cut).
- До и после награды gameplay различим: Auto Bass/Riser/Hard Cut имеет слышимый либо управляющий эффект.
- Scoring не зависит от FPS; clamp Hype [0,100], Reputation≥0.
- Два события с одним ID не удваивают reward.
- Победа первого сета не заканчивает забег: экран результата и второй сет. Победа второго сета или любое поражение заканчивает забег; есть Reset/new run. Карточки между сетами — DJ-014.
- Финиш 1-го сета требует Hype≥60, 2-го Hype≥65 плюс дополнительное условие.

### UI / Accessibility

- Игрок понимает 4 действия DJ-пульта без внешнего объяснения после короткого tutorial.
- Android важные touch-targets имеют минимум ~48dp, safe area корректна.
- Текущий трек/активная дека/бит/цель видны без цветового различения.
- Reduced flashing полностью выключает strobes и интенсивные flash.
- В Web ошибки звукозапуска/загрузки дают Retry вместо «тишина и проигрыш».

## MVP не готов, если

- Web build играет только через native фильтр и часть функций молчит.
- Игрок набирает Hype многократным переключением bass kill без слышимого результата.
- В Android нельзя выполнить переход без клавиатуры.
- Каждое выступление выглядит одинаково и upgrade никак не влияет на второй сет.
- Разные платформы дают принципиально разные правила scoring.

## Definition of Done для каждой P0 задачи

1. Есть документ требований и тестов.
2. Реализовано в отдельной ветке, нет критических ошибок компиляции.
3. Unit/PlayMode tests проходят для затронутых правил.
4. Проверено хотя бы на Windows + Web + Android smoke (если platform sensitive).
5. Описан reproducible manual test и подтверждён acceptance.
6. Обновлены профильный .md, GDD/MVP при изменении правил.
7. В PR указаны риски, скрин/видео/аудиодемонстрация для визуальных/аудио задач.

## Exit criteria к публичной демоверсии

- Предварительный playtest 8–12 человек, ≥60% добровольно повторяют забег (рабочая гипотеза).
- Нет crash/blocker в обязательных браузерах и тестовом Android.
- Музыка и sample packs легальны для всех заявленных дистрибуций.
- Пройдены QA с фокусом на слуховые дефекты, зрительное восприятие, паузы и touch.
- Готовы инструктаж, настройки звука, экран лицензий/credits, способ сообщить о проблеме.

# 16. QA strategy / Test Matrix

## Приоритет тестирования

1. Звук и кроссплатформенность (critical).
2. Корректность очков и антиэксплойты.
3. Input и UI на Android.
4. Пауза, восстановление после скрытой вкладки/звонка.
5. Стабильность памяти, FPS, браузерных скачков производительности.
6. Доступность, локализация, визуальные состояния.

## Матрица платформ (минимальная)

| Платформа | Build | Input | Audio risks | Дополнительно |
|---|---|---|---|---|
| Win 10/11 | native x64 | mouse + keyboard | WASAPI/device switch | window/fullscreen |
| Chrome Win | Web | mouse + keyboard | autoplay, AAC gap, hidden tab | cache + cold load |
| Firefox Win | Web | mouse + keyboard | scheduling, audio context | WebAssembly |
| Edge Win | Web | mouse + keyboard | autoplay, AAC gap | cache/permissions |
| Android средний | native arm64 | 2-finger touch | focus, BT latency, thermal | safe area 20:9 |
| Android планшет | native arm64 | touch | audio interruptions | 16:10 UI |
| Safari macOS | Web | mouse + keyboard | browser audio/time | P1 until available |

Фиксировать версии OS/browser/device model и сборки в каждом отчёте. «Работает на моём ПК» не считается platform QA.

## Автоматические domain tests

- `MusicClock`: 120 BPM, 4/4, фраза 8 bars; nearest future boundary never in past; seek after resume.
- `Hype`: clamp [0,100], one-shot event IDs, no score during Pause.
- `Transition`: A dominance -> B dominance, once; jitter/bounce same window not duplicate.
- `BassConflict`: sustained >threshold, no trigger on 1-frame overlap, cooldown.
- `Drop`: build-up≥1bar, return on phrase boundary, cooldown, fake toggle excluded.
- `RewardRoll`: 2 distinct from 3; seeded deterministic; selected applies exactly once.
- `RunFlow`: win/lose, reward only between stages; Reset clears modifiers.
- `InputCommand`: invalid state rejection; scheduling ack; race conditions queued starts.

## Manual audio test procedures

### QA-A01: Двухдековый phase alignment

1. Запустить A, затем B на ближайший такт.
2. Включить тестовый click/drum reference на двух деках.
3. Проверить на 0, 1, 3, 5 мин, нет ли слышимого флейма/эхо и накопления сдвига.
4. Снять screen/audio recording или loopback capture, оценить offset; целевой ≤20 мс после 5 мин (процедура измерения должна быть повторяемой).

### QA-A02: Gapless loops

1. Запустить одну пластинку с отчётливой атакой на bar 1.
2. Прослушать/записать 50 повторов в desktop native и каждом Web browser.
3. Проверить нет ли длинного silent gap, click, пропущенной атаки или «двойной» доли.

### QA-A03: Crossfade/Bass Kill/Filter

1. Перевести crossfader `0→0.5→1`; убедиться, что звук соответствует кривой и нет внезапного gain jump.
2. Выключить LOW у A, остальные два stems должны оставаться.
3. Поэкспериментировать с filter cutoff; проверить *слышимый* low-pass на каждом обязательном target.
4. 100 резких управляющих действий без клиппинга и double event.

### QA-A04: Interruptions

- На Web: 20 раз свернуть/вернуть вкладку; браузер блокирует audio until user gesture? UI показывает Resume, без потерь Hype.
- На Android: screen off, incoming call, смена BT на dynamic output; после возобновления не теряется beat origin.
- На PC: alt-tab/fullscreen change/устройство аудиовывода; не происходит неконтролируемый restart.

## Gameplay exploits

- Изменять Bass Kill 10 раз за такт: не фармить Hype.
- Ползунок туда-обратно между 0.35 и 0.65: нет спама Clean Transition.
- Начать новую деку на нулевой громкости и мгновенно остановить: не дают награду.
- Скомбинировать Riser с повторяющимся drop: срабатывает cooldown.
- Получить два reward с одинаковым eventId — только одна активация.

## Performance targets — цели, не обещания

| Среда | Цель FPS | Что записывать |

| PC | 60 | frame-time 95th percentile, аудио dropout |

# 17. Playtests, telemetry и баланс

## Принцип

MVP не требует сервера и онлайн-аналитики. Для закрытых плейтестов можно собирать **локальный анонимный отчёт по согласию**. Не хранить музыку пользователя, записи микрофона, имена, постоянные идентификаторы устройства или точную геолокацию.

## Цели

- Сколько времени нужно до первого чистого перехода.
- Делают ли игроки осмысленные build-up/drop.
- Понимают ли награды и меняется ли стиль игры после выбора.
- На каких платформах возникают проблемы со звуком.
- Где появляются справедливые/несправедливые поражения.

## Пример событий

| Event | Properties (без PII) |
|---|---|
| `run_started` | buildVersion, platform, rngSeed (локально), tutorialCompleted |
| `club_started` | clubRuleId, startHype, trackPoolIds |
| `deck_start_scheduled` | deck, beatIndex, quantizeMode |
| `transition_completed` | transitionType, quality, HypeDelta |
| `drop_completed` | chargeBars, rewardApplied, HypeDelta |
| `bass_conflict` | durationBeats, HypeDelta |
| `reward_chosen` | choiceId, offeredIds |
| `club_finished` | result, finalHype, reputation, durationBars |
| `audio_error` | platform, backend, errorCode (без raw payload) |
| `run_finished` | result, duration, retries |

## Основные метрики

- **Tutorial completion rate**.
- **Time to first Clean Mix**.
- **Run completion rate**.
- **Second-run voluntary rate** (повторный старт без подсказки).
- **Distribution of Hype** в конце первого/второго выступления.
- **Audio interruption errors per 30 minutes**.
- **Upgrade pick rate** и улучшение результата после награды.

## Баланс-эксперименты

1. Сначала только качественный плейтест (8–12 человек).
2. Если большинство проигрывает слишком быстро — проверить ясность действий, а не автоматически повышать награды.
3. Если все выигрывают без различий в стилях — проверить анти-фарм, штрафы и клубный вкус.
4. Изменять за итерацию **1–2 числовых параметра**, записывать build hash.
5. Не делать выводы о retention и коммерческом спросе из 8–12 тестировщиков; для этого нужен отдельный этап.

## Privacy и storage

- Default: telemetry отключена. Debug log хранится локально и удаляется пользователем.
- Если появится online analytics: разрешение/информирование, privacy policy, minimization, опции отказа/удаления в рамках применимых правил. Не добавлять сторонние SDK до подтверждения необходимости.
- Показ аудиозаписи/видео плейтеста только по отдельному согласию участников.

# 18. Релиз, позиционирование и правовые вопросы

## Предлагаемая стратегия релиза

**Шаг 1:** бесплатная закрытая/публичная **PC + Web demo**, чтобы подтвердить core fun и качество Audio/Web.  
**Шаг 2:** native Android test build и улучшение touch; публикация по актуальным требованиям площадки.  
**Шаг 3:** платный полноценный PC game + Android premium или free demo→one-time unlock — решить после теста рынка.  
**Шаг 4:** дополнительные клубы/музыка как content updates; не делать обязательную механику через покупки.

Это **стратегические предложения**, а не утверждения об одобрении конкретной платформой.

## Рекомендуемая монетизация

Для первого коммерческого выпуска: **premium buy-to-play** на PC; Web — короткая бесплатная демоверсия для привлечения; Android — премиум или одна разблокировка полной игры. Не добавлять рекламу посреди сета: прерывание музыки ломает центральную механику. Рекламу на порталах Web можно рассматривать только при полной паузе и прозрачном пользовательском опыте, отдельно от MVP.

## Позиционирование

- Elevator pitch: «Своди музыку, чтобы победить. Собери уникальный DJ-билд и покори клубы пиксельного города».
- Первые 5 секунд трейлера: руки над пультом, реальный crossfader mix, реакция танцпола.
- Показать «до/после» upgrade: автоматическая очистка баса, riser, hard cut.
- Не рекламировать как профессиональный DJ-симулятор, если не поддерживаем ручной beatmatching.

## Какие материалы подготовить к демо-релизу

- Trailer 30–60 сек с **записанным игровым звуком**, не подложенной песней.
- 4–6 screenshots 16:9 + мобильный экран.
- Описание и краткий feature list RU/EN.
- Credits/лицензии для музыкальных loops, плагинов, шрифтов и графики.
- Публичный email/форма bug-report (создать перед релизом).
- Privacy policy — если собирается аналитика/данные или этого требует магазин.
- Known issues, совместимость браузеров, сведения о доступности.

## Право на музыку — обязательно

- Указать автора композиции, обладателя мастер-прав, источник каждого сэмпла.
- Проверить разрешения на **интерактивную обработку, встраивание в компьютерную/мобильную игру, использование в браузере, распространение в нескольких странах**.
- Получить права на рекламные записи/трейлер, если композиция туда попадёт.
- Отдельно определить право выпускать музыку как OST за пределами игры.
- Правообладатели сторонних треков, известных сэмплов и модов не наследуют автоматически «игровую» лицензию.
- Для договоров и правовых решений при коммерческом релизе обратиться к профильному юристу.

## Технические/регуляторные проверки перед публикацией

- Unity лицензирование по актуальным на дату релиза условиям.
- Возрастной рейтинг и content disclosures там, где нужны.
- Google Play target API level, правила SDK, персональных данных и тестирования — **проверять непосредственно перед выкладкой**, поскольку требования меняются.
- Правила браузерных/игровых порталов на загрузку WebAssembly/аудио и рекламу.
- Авторские права на выбранный шрифт с кириллицей и UI-звуки.
- Логотип/название — поиск потенциальных конфликтов с торговыми марками до маркетинга.

## Что НЕ закладываем в MVP

Серверные покупки, ads mediation, случайные платные loot boxes, платная энергия, account login, live ops, user generated content, multiplayer, рейтинговые онлайн-таблицы.

## Финансовые вопросы для отдельной таблицы бюджета

Музыка (композитор/DAW/mixing/mastering), пиксель-арт (авторские права), тестовые Android-устройства, публикация/маркетинг, возможные плагины, юридическое оформление. Без реальных ставок и договоров **не выдумываем бюджет**.

## 2. Допущения

- Все стартовые треки будут музыкально совместимы при 120 BPM.
- Первые два сета могут пройти в одном клубе, не создавая скуки.
- Два типа перехода и один детектор дропа дадут достаточно механической глубины на 5–7 минут.
- Один разработчик может поддерживать Windows, Web и Android при простой графике; WebAudio spike может существенно удлинить работу.
- Игра остаётся fun без сложной экономической меты.

Каждое допущение должно пройти тест или получить изменённый дизайн.

## 3. Архитектурные решения (ADR)

### ADR-001 — Единый домен и адаптеры платформ

**Статус:** Accepted (design).  
**Решение:** scoring/game rules в чистом C#; audio/input/platform integrations через интерфейсы.  
**Причина:** одна версия игры на PC/Web/Android, разные технические ограничения.  
**Компромисс:** небольшой дополнительный код абстракций в MVP.

### ADR-002 — Fixed BPM 120, 8-bar stems в MVP

**Статус:** Accepted (design).  
**Решение:** 4 трека×3 stems, 120 BPM/4-4/8 bars.  
**Причина:** исключить на старте time-stretching, ключевые несовместимости и сложную автоаналитику.  
**Компромисс:** повторение контента; позже добавлять вариации B секции.

### ADR-003 — Web audio implementation

**Статус:** **Pending — решение принимается после DJ-004**.  
**Вариант A:** Unity Web `AudioSource`/PlayScheduled с stem volume; low-pass только через проверенный replacement (например, pre-rendered).  
**Вариант B:** JS Web Audio `AudioBufferSourceNode`+`GainNode`+`BiquadFilterNode` через `.jslib`.  
**Критерий:** 50 gapless loops, 5-min sync, pause/resume, реальный audible filter, download/memory и риск поддержки.  
**Правило:** не разрабатывать все новые эффекты до выбора варианта. Не оставлять фильтр на Android/PC, если на Web заявлен идентичный функционал, но он не работает.

### ADR-004 — Android native, landscape

**Статус:** Accepted (design).  
**Причина:** аудиоустойчивость/UX, не зависеть от браузерного WebView.  
**Последствие:** отдельная touch-панель и Android QA.

### ADR-005 — Release: free demo first

**Статус:** Proposed.  
**Причина:** нишевая идея требует validation; реклама посреди выступлений разрушает core gameplay.  
**Обратимость:** бизнес-модель утверждается после плейтестов и платформенных ограничений.

### ADR-006 — Scene PixelPerfect / UI resolution separation

**Статус:** Accepted (design).  
**Причина:** пиксельный клуб может жить на 480×270, но интерфейс на телефоне должен сохранять читаемость независимо от кратности пикселя.

### DJ-013 — два сета `club_neon_basement`

Клуб один, сета два. На старте каждого сета Hype = `initialHype` (35) и между сетами не переносится. Reputation забега копится. Combo нового сета снова ×1. Очки пишутся только в фазе Performing, и один id события даёт награду один раз. Пауза, свёрнутая вкладка и потеря audio focus не меняют Hype и не двигают таймер сета.

Поражение приходит сразу, если Hype = 0 дольше одной фразы (16 с): reason `hype_floor`. Ноль на одном тике сет не обрывает. Таймер вышел, а цель сета не взята: reason `timeout`.

Сет 1 — обучение. Победа при Hype ≥ 60, поле `rules` молчит. Экран результата ведёт во второй сет.

Сет 2 побеждает при Hype ≥ 65 и ровно одном правиле, которое seed забега выбирает из `rules`. `perform_one_clean_drop`: за сет принят хотя бы один `ScoreKind.Drop`; иначе `clean_drop_missing`. `maintain_energy` запирает уже существующий `ScoreKind.StaleGroove` (`stale-{phrase}`, Hype −4): событие применено — reason `energy_lost`. `PhraseDecay` (`decay-{phrase}`, Hype −2) в это правило не входит. `SetJudge` ставит его на каждой границе фразы при любом миксе, и запрет сделал бы сет непроходимым на 16-й секунде. Игрок удерживает энергию тем, что не даёт одному и тому же груву доминирующей деки и пластинки дойти до `StaleGroove`.

Победа сета 2 или любое поражение заканчивает забег и делает Reset.

Пример одного такта. LOW был ниже 0.20 весь предыдущий такт; на доле «раз» следующего такта LOW снова выше 0.75, и дека слышна. Игрок слышит, как кик и бас встают на сильную долю. Текущий код даёт `ScoreKind.Drop` (`drop-{bar}`) и Hype +12. Одного такого Drop достаточно для `perform_one_clean_drop`.

Вне среза: карточки апгрейдов (DJ-014), новые жанры, смена порогов 35/60/65, карта клубов P1.

## 6. SaveGame / Settings (shell, schemaVersion 1)

Один локальный документ. Mid-run snapshot **отсутствует**. Чистые типы: `DeckRogue.Core.Save` (`SaveGameDocument`, `SettingsData`, `SaveFlushTrigger`).

```json
{
  "schemaVersion": 1,
  "settings": {
    "language": "ru",
    "musicVolume": 0.8,
    "sfxVolume": 0.7,
    "uiScale": 1.0,
    "reducedFlashing": false,
    "tutorialCompleted": false
  },
  "unlockedTrackIds": [],
  "unlockedGearIds": [],
  "unlockedClubIds": [],
  "bestReputation": 0
}
```

| Поле | Пишется когда | Заметки |
|---|---|---|
| `settings.*` | `SaveFlushTrigger.SettingsChanged` | Volumes clamp 0..1; `uiScale` 0.75..1.5; пустой `language` → `ru` |
| `unlockedTrackIds` | `MetaUnlockChanged` (Act1: boss → `track_signal_carrier`) | Boot → `MetaUnlocks.Hydrate`; Lose **не** чистит |
| `unlockedGearIds` | — | **Резерв, всегда `[]` в Act1** (run upgrades не meta) |
| `unlockedClubIds` | — | **Резерв, всегда `[]` в Act1** (pool без meta-gate) |
| `bestReputation` | `RunEndedBestReputation` при `FinalResult`, только если run Rep выше | ≥ 0; не mid-run |

**Миграция:** `SaveGameDocument.Migrate`: null/0/future → fill known fields, `schemaVersion = 1`, gear/club force empty, track ids dedupe. Не хранить необязательные персональные данные / cloud ids.

**Boot:** load → Migrate → apply Settings → `ApplyToMeta` → держать `BestReputation` для сравнения на конце забега.

## 7. Правила идентификаторов

- Треки: `track_snake_case`.
- Клубы: `club_snake_case`.
- Upgrades: `upgrade_snake_case`.
- События: стабильные enum/string keys, локализуемые labels не используются как ID.
- Никаких GUID от Unity Asset в игровых сохранениях без явного mapping/migration.

## 8. Локализация

Текст для игроков — по `locKey`/таблице RU/EN. Модели данных не зависят от русского displayName. Для early MVP русская UI-линия допустима, но архитектура сразу поддерживает смену языка без переписывания ID.

# 21. Первые инженерные задания (mentor workflow)

> Цель: писать код самостоятельно. Здесь — **требования, ограничения, проверка**, но нет готовых реализаций. Каждая задача завершается PR/коммитом, тестами и заметкой о том, чему научился.

## DJ-001 — Bootstrap + three platform targets

**Контекст:** новый Unity 2D проект.  
**Задача:** создать репозиторий, `.gitignore`, базовые каталоги, пустую сцену и Build Profiles для Windows/Web/Android.  
**Ограничения:** Unity 6.3 LTS как рекомендованная стартовая ветка; не импортировать тяжёлые asset packages; арт placeholders.  
**Acceptance:** три билда показывают одну сцену с номером версии; Android запускается на тестовом девайсе; Web открывается через HTTP/HTTPS, не `file://`.  
**Тест:** screenshot всех трёх.  
**PR:** `feature/DJ-001-bootstrap`; добавить фактическую версию Unity в README.

## DJ-002 — MusicClock

**Контекст:** gameplay не должен зависеть от FPS.  
**Задача:** абстрагировать time provider, считать beat/bar/phrase, вычислять будущие границы.  
**Ограничения:** запрет `Time.deltaTime` как основного источника фазы; нет UI/аудиодек.  
**Acceptance:** at 120 BPM boundary каждые 0.5/2/16s; request too late shifts to *next* available beat/bar; unit test с fake time provider.  
**Тест:** 10 программных кейсов с times around boundary.  
**PR:** `feature/DJ-002-music-clock`.

## DJ-003 — Native two-deck playback

**Контекст:** проверить реальное удовольствие от сведения.  
**Задача:** 2 деки и 3 stems на каждой; scheduling на DSP clock; загрузка двух тестовых композиций.  
**Ограничения:** только два track definitions, все фиксированные BPM и длины; никаких бонусов.  
**Acceptance:** слышимая синхронизация 5 мин, 50 loops; без double starts / clicks.  
**Тест:** записать переход A→B с отключением LOW.

## DJ-004 — Web Audio Spike (главный gate)

**Контекст:** без Web невозможно обещать порт.  
**Задача:** собрать Web билд DJ-003, проверить `PlayScheduled`, loops, AudioMixer bass volume и low-pass. При необходимости сделать minimal `.jslib` proof-of-concept для Web Audio.  
**Ограничения:** не добавлять полноценную игру, магазин, новые FX.  
**Acceptance:** видео/аудиозапись Chrome+Firefox и ADR-003 с решением по бэкенду, оценкой памяти/сложности и планом фильтра.  
**Тест:** 50 loops, 5 min, 20 hide/resume.

## DJ-005 — Pause and interruption

**Задача:** пауза и рестарт музыкального timebase при Web tab hide/Android audio focus loss.  
**Acceptance:** никакие штрафы Hype во время mute/suspend; после resume деки снова в фазе, или пользователь получает явный `Restart set`.

## DJ-006/007 — TrackLibrary + mixer controls

**Задача:** хранить 4 track definitions; crossfader equal power; Bass Kill on stem LOW; native и Web одинаково понимают команды.  
**Acceptance:** mouse/keyboard/touch управляют звуком, нет clipping/щелчков.  
**Тест:** 100 быстрых drag/toggle и проверка изменения звука.

## DJ-008 — Cross-platform filter

**Задача:** добавить **реальный** low-pass на каждой платформе, основанный на решении DJ-004.  
**Acceptance:** по частотной характеристике/слуху фильтр меняет спектр; на Web нет неработающего UI.  
**Stop condition:** если фильтр требует непропорциональных усилий — пересмотреть P0 scope одинаково для всех целевых сборок.

## DJ-009/010/011/012 — Input → Scoring vertical slice

**Задача:** InputAdapter, TransitionEvaluator, BassConflict, DropDetector, Hype/Combo/Reputation.  
**Acceptance:** события считаются один раз, мышь и multitouch не порождают дубли; Hype clamped; все фразы измеряются audio clock.  
**Тест:** FakeAudio clock in EditMode; negative test cases из [QA](#section-17).

## DJ-013 — два сета `club_neon_basement`

**Задача:** два сета по контракту DJ-013 в ClubDefinition. Сет 1 — обучение, победа при Hype ≥ 60, затем экран результата и второй сет. Сет 2 — Hype ≥ 65 и одно правило из seed. Победа сета 2 или любое поражение → финал забега и Reset.  
**Вне среза:** карточки апгрейдов.  
**Acceptance:** reasons `hype_floor`, `timeout`, `clean_drop_missing`, `energy_lost`; пауза не двигает таймер и не штрафует; один event id — одна награда; очки только в Performing.

## DJ-014 — награда между сетами

**Задача:** после первого сета предложить 2 из 3 improvements, игрок берёт 1; эффект слышен или меняет управление во втором.  
**Acceptance:** seed воспроизводим, выбранный upgrade применяется один раз и в MVP не стакается.

## DJ-015/016/017/018 — UI, арт, QA и playable build

**Задача:** desktop/touch UI, базовая пиксельная сцена, толпа, обучение, настройки, reduced flashing, end-to-end QA.  
**Acceptance:** [MVP acceptance](#section-15) целиком; нет browser-only, device-only функций, которые ломают основные механики.

# 22. Глоссарий

| Термин | Объяснение |
|---|---|
| DJ / диджей | Человек, соединяющий музыку в непрерывный сет и управляющий её развитием |
| Deck / дека | Независимый проигрыватель пластинки (A или B) |
| Track / пластинка | В этой игре — набор синхронных stems одного музыкального грува |
| Stem | Отдельный аудиослой композиции (LOW/PERC/MUSIC) |
| BPM | Beats per minute, количество долей за минуту |
| Beat / доля | Минимальный основной пульс, здесь 0.5 с при 120 BPM |
| Bar / такт | Группа долей, здесь 4 доли = 2 секунды |
| Phrase / фраза | Группа тактов, здесь 8 тактов = 16 секунд |
| Quantize | Привязка старта/команды к музыкальной сетке |
| Beatmatching | Выравнивание темпов/фаз двух композиций |
| Crossfader | Ползунок, регулирующий соотношение слышимости A и B |
| EQ | Эквалайзер — регулировка частотных диапазонов |
| Bass Kill | Отключение/приглушение низкочастотной секции |
| Low-pass | Фильтр, ослабляющий высокие частоты |
| Build-up | Подготовка музыкального напряжения |
| Drop | Возврат/вход мощного ритмического элемента после build-up |
| Hype | Энергия/вовлечённость публики, ресурс успешности |
| Combo | Множитель репутации за цепочку музыкальных решений |
| Reputation | Очки качества выступления |
| Roguelite | Забеги с рандомом/поражением/началом сначала и потенциальными постоянными unlocks |
| DSP time | Аудиотаймлайн, не зависящий напрямую от частоты кадров |
| Audio backend | Реализация звукового воспроизведения для платформы |
| PlayScheduled | Запуск AudioSource к заданному времени аудиосистемы Unity |
| Web Audio API | Браузерный API для проигрывания/обработки звука |
| AudioContext | Контекст времени/графа браузерного Web Audio API |
| WebAssembly / WebGL | Технологии исполнения кода/рендеринга Unity в браузере |
| AAC glitch | Возможный разрыв/артефакт на петле из-за перекодирования аудио |
| Pixel-perfect | Отображение пиксель-арта без нежелательного размытия и дрожания |
| Native Android | Android приложение, собранное непосредственно под Android, не браузерная страница |
| Audio unlock | Первое пользовательское действие, после которого браузер разрешает воспроизведение |
| ADR | Architecture Decision Record — документ о важном инженерном решении |
| P0/P1/P2 | Обязательно для MVP / следующая версия / позже |
| MVP | Первая минимальная полноценная версия для проверки гипотез |

## Что из этого является проектным решением, а не «фактом Unity»

- `480×270`, `120 BPM`, 3 stems, 4 пластинки, 2 выступления, 50 loops, 5-minute drift ≤20ms — **наши проектные решения/QA ориентиры**.
- WebAudio browser backend — **вариант проектной архитектуры**, не встроенная универсальная фича Unity.
- `48dp`, `30/60FPS`, `<50MB` — **целевые бюджеты**, требующие validation.
- Будущие требования Google Play/других магазинов — **не фиксируются как актуальные цифры** в этой документации, проверяются перед публикацией.
